This walkthrough drives one credential through its whole life on the **hosted Didit ID demo**: create a schema, issue it by email, claim it into a passkey-backed wallet, and verify it with selective disclosure. Nothing to install — everything runs in your browser against the live environment. Budget about 10 minutes.

## Prerequisites

- **A passkey-capable browser** — Chrome, Safari, or Edge on a device with a platform authenticator (Touch ID, Windows Hello) or a security key.
- **An email address you can read** — the console and wallet email you a one-time code, and the credential offer arrives by email too. Any domain works.

## The hosted apps

Three browser apps, all backed by one API.

| App | What it is | URL |
| --- | --- | --- |
| Console | Issuer + verifier operator app | [`console-idv0.staging.didit.me`](https://console-idv0.staging.didit.me/console) |
| Holder wallet | Where credentials live (in your browser) | [`wallet-idv0.staging.didit.me`](https://wallet-idv0.staging.didit.me) |
| VeriBank | Relying-party (verifier) demo | [`veribank-idv0.staging.didit.me`](https://veribank-idv0.staging.didit.me) |
| API | The service all three call | `https://idv0.staging.didit.me` |

<Note>
  Passkeys are bound to the `didit.me` domain, so the console and wallet share the same passkey — sign in to either with the same account.
</Note>

## Walkthrough

<Steps>
  <Step title="Sign up in the console">
    Open the [console](https://console-idv0.staging.didit.me/console) and create an account with any email. You'll get a one-time code by email — enter it to confirm. On first sign-in the console bootstraps your credentials tenant and its API key. See [programmatic access](/guides/programmatic-access) for the same flow via the API.
  </Step>

  <Step title="Create an EmployeeBadge schema">
    In the console, create a credential schema with `vct` = `EmployeeBadge` and three selectively disclosable attributes: `employee_id`, `role`, and `department`. This is the equivalent of [`POST /v1/credential-schemas`](/api-reference/credentials/credential-schemas-post).
  </Step>

  <Step title="Issue the credential by email">
    Create a credential offer for the badge with your own email as `recipient_email` and `send_email: true`. The console fills in the claim values (for example `employee_id: E-1042`, `role: Engineer`, `department: Platform`). See [issue via email](/guides/issue-via-email). You'll receive a **claim link** by email; keep the transaction code the console shows you.
  </Step>

  <Step title="Create a wallet account with a passkey">
    Open the [wallet](https://wallet-idv0.staging.didit.me) and create an account. The wallet uses a passkey (WebAuthn) for account sign-in and generates a WebCrypto ES256 holder key per credential. Approve the passkey prompt in your browser.
  </Step>

  <Step title="Claim the credential">
    Open the claim link from your email in the wallet (or paste it in). Review the offer, enter the transaction code, and claim. The wallet runs the [OpenID4VCI](/concepts/openid4vci) exchange — token, nonce, holder proof — and stores the SD-JWT VC bound to a fresh holder key. See the [wallet quickstart](/wallet/quickstart).
  </Step>

  <Step title="Verify with selective disclosure">
    Open [VeriBank](https://veribank-idv0.staging.didit.me) and pick a scenario. It requests a presentation (for example, the badge `role`). Scan the QR with the wallet or use the same-device link, approve the disclosure of only the requested claim, and the demo polls for the verdict. The verifier learns `role` and nothing else. See [build a relying party](/guides/relying-party).
  </Step>
</Steps>

## What you just proved

- An issuer defined a credential type and issued it by email — no wallet pre-provisioning.
- A holder claimed it into a browser wallet with a passkey account and per-credential holder keys.
- A verifier confirmed one claim without the holder revealing the rest.
