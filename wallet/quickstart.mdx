---
title: "Wallet quickstart"
description: "Run the holder wallet locally, create a passkey account, claim a credential from an email link, and present it to a verifier with selective disclosure."
---

Take a credential from an emailed claim link to a verified presentation in a few minutes: run the wallet on your machine, create an account with a passkey, claim the credential, then answer a verifier's request while disclosing only what it asks for.

<Note>
  This quickstart assumes the credentials service is running at `https://idv0.staging.didit.me` and an issuer has created an emailed offer (see [issue via email](/guides/issue-via-email)). To bring up the whole stack at once, follow [run the full demo](/demo).
</Note>

<Steps>
  <Step title="Run the wallet locally">
    Start the wallet on port `3012`, pointed at the local service. The two public base URLs it needs:

    ```bash
    # in the didit-credentials-wallet repo
    export NEXT_PUBLIC_API_BASE="https://idv0.staging.didit.me/v1"
    export NEXT_PUBLIC_AUTH_BASE="https://idv0.staging.didit.me"

    pnpm install
    pnpm dev   # serves https://wallet-idv0.staging.didit.me
    ```

    `NEXT_PUBLIC_API_BASE` is where the wallet calls the OpenID4VCI and OpenID4VP protocol endpoints. `NEXT_PUBLIC_AUTH_BASE` is where it runs the passkey account ceremonies. Neither uses a tenant API key.
  </Step>

  <Step title="Create an account with a passkey">
    Open `https://wallet-idv0.staging.didit.me` and create an account. The wallet runs a WebAuthn registration ceremony — approve the passkey prompt (Touch ID, Windows Hello, or a security key). The passkey signs you into the account; it is separate from the per-credential holder keys the wallet generates later. See [wallet security](/wallet/security) for why the two are distinct.
  </Step>

  <Step title="Receive a claim email (or paste the link)">
    An issuer that created an emailed offer sends a claim link of the form:

    ```
    https://wallet-idv0.staging.didit.me/claim?offer=<offer_id>
    ```

    Open the link, or paste it into the wallet's claim screen. The wallet also accepts a raw offer code or a scanned QR. In local dev without Postmark, grab the link from the service's dev inbox:

    ```bash
    curl "http://localhost:8011/v1/dev/last-email?to=<your-email>" | jq -r '.claim_url'
    ```
  </Step>

  <Step title="Claim the credential">
    The wallet previews the offer and, when the offer requires one, prompts for the transaction code (PIN) the issuer shared with you. On confirm, it runs the OpenID4VCI exchange end to end:

    1. Resolve the offer document and read the pre-authorized code.
    2. Redeem the code (and the PIN) at `POST /v1/oauth/token`.
    3. Generate a fresh non-extractable ES256 holder key.
    4. Mint a single-use `c_nonce` at `POST /v1/nonce` and sign an `openid4vci-proof+jwt`.
    5. Receive the SD-JWT VC from `POST /v1/credential`.
    6. Verify the credential's `cnf.jwk` matches the key it just generated, then store both in the vault.

    <Warning>
      Enter the transaction code carefully. The offer locks after five failed attempts, and you have to ask the issuer for a new one.
    </Warning>
  </Step>

  <Step title="Open the relying-party demo">
    Open the relying-party demo at `https://veribank-idv0.staging.didit.me`. It creates a presentation request (for example, asking for the badge `role`) and shows a QR code plus a same-device link into the wallet at `https://wallet-idv0.staging.didit.me/present?request=<uuid>`.
  </Step>

  <Step title="Present with selective disclosure">
    Open the present link. The wallet fetches the request, matches it against your stored credentials, and shows a consent screen with exactly the claims the verifier asked for. Approve, and the wallet:

    1. Selects only the requested disclosures (issuance order preserved).
    2. Builds a key-bound presentation — the KB-JWT commits to the presented part with the verifier's `aud` and `nonce`.
    3. Submits the `vp_token` to `POST /v1/presentations/{uuid}/response`.

    The demo polls for the verdict. The verifier learns only the disclosed claim, and nothing else in the credential.
  </Step>
</Steps>

## Troubleshooting

<AccordionGroup>
  <Accordion title="The passkey prompt never appears or fails">
    Passkeys need a WebAuthn-capable browser and a platform authenticator (Touch ID, Windows Hello) or a security key. Use Chrome, Safari, or Edge on a supported device. On `localhost`, WebAuthn works over `http`; on any other host it requires `https`. If you dismissed the prompt, the wallet treats it as a cancel, not an error — retry the account step.
  </Accordion>
  <Accordion title="Requests to the service fail with a CORS error">
    The service allows the wallet origin (`https://wallet-idv0.staging.didit.me`) only in dev settings. Run the service with `DJANGO_SETTINGS_MODULE=core.settings.devserver` (what `make dev-all` uses). If you serve the wallet on a different port or host, add it to the service's `CORS_ALLOWED_ORIGINS`.
  </Accordion>
  <Accordion title="The transaction code (PIN) is rejected">
    The PIN comes from the issuer out-of-band — it is never in the claim email. Confirm you are entering the exact code the issuer gave you. After five wrong attempts the offer locks; ask the issuer to resend, which mints a fresh offer window.
  </Accordion>
  <Accordion title="The offer says 'not found' or 'expired'">
    Offers are single-use and time-limited. An offer that was already claimed, or whose window elapsed, returns 404 on purpose. Ask the issuer to resend the claim email (`POST /v1/credential-offers/{uuid}/resend-email`).
  </Accordion>
  <Accordion title="'No matching credential' when presenting">
    The wallet only offers credentials whose `vct` matches the request and that carry every requested claim. Claim a credential of the requested type first, then retry the presentation.
  </Accordion>
</AccordionGroup>
