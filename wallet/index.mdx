The Didit holder wallet is the holder-facing half of Didit ID. It runs in the browser, backs the account with a passkey, generates a WebCrypto holder key per credential, stores everything in IndexedDB, and speaks [OpenID4VCI](/concepts/openid4vci) to claim credentials and [OpenID4VP](/concepts/openid4vp) to present them. It never sees a tenant API key — it only calls the public holder and verifier protocol endpoints.

Use it as the reference wallet for the whole flow: an issuer emails a claim link, the holder opens it in the wallet, claims the [SD-JWT VC](/concepts/sd-jwt-vc), and later presents only the claims a verifier asks for.

## What the wallet is

- **Browser-based.** A Next.js app served at `https://wallet-idv0.staging.didit.me` in local dev. No native install, no server-side holder state.
- **Passkey account.** Sign-in uses a passkey (WebAuthn). The passkey authenticates the account — it is not the credential holder key.
- **WebCrypto holder keys.** Each credential is bound to its own non-extractable ECDSA P-256 (ES256) signing key generated with WebCrypto. The public key goes into the credential's `cnf.jwk`; the private key never leaves the browser.
- **IndexedDB storage.** Credentials, per-credential keys, activity, and cached status lists live in a local IndexedDB vault, scoped per account.
- **Standards-native.** SD-JWT VC issuance and presentation, OpenID4VCI for claiming, OpenID4VP with DCQL for presenting, and IETF Token Status List for revocation checks.

## When to use it

<CardGroup cols={2}>
  <Card title="Use the Didit wallet" icon="circle-check">
    You want holders to claim and present credentials today without shipping your own wallet. You are running the demo, prototyping, or handing users a browser wallet for reusable credentials.
  </Card>
  <Card title="Build your own" icon="hammer">
    You need a native app, cloud backup and multi-device sync, device attestation, or deep integration into an existing product. Follow the [holder-wallet guide](/guides/holder-wallet) to implement the same protocol flows yourself.
  </Card>
</CardGroup>

The wallet and a custom implementation talk to the exact same public endpoints, so you can start on the Didit wallet and move to your own later without changing the issuer or verifier side.
