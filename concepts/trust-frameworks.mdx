Trust frameworks group issuers under a governance model. A verifier can trust an entire framework, trust individual issuers, or block specific issuers inside a framework it otherwise accepts.

Didit ID applies trust policy automatically during [OpenID4VP verification](/guides/verification). A credential can be correctly signed, unexpired, and active, but still fail if its issuer does not match the trust policy for the relying party.

## The policy model

Trust is policy, not a flat list.

<Steps>
  <Step title="Choose frameworks">
    Trust frameworks define governed issuer groups. Trusting a framework accepts credentials from its member issuers unless you add an override.
  </Step>
  <Step title="Add individual issuers">
    Add an issuer directly when you want to trust one issuer without trusting the whole framework it belongs to.
  </Step>
  <Step title="Block exceptions">
    Add a per-issuer override to block a specific issuer inside a trusted framework.
  </Step>
  <Step title="Select the relying-party policy">
    Each relying party can inherit the account policy or define its own accepted frameworks and issuers.
  </Step>
  <Step title="Verify automatically">
    Didit ID evaluates the credential issuer against the selected policy during verification. You do not wire policy into every presentation request.
  </Step>
</Steps>

## Didit Network

The **Didit Network** is a governed framework representing every issuer on the Didit platform. New accounts trust the Didit Network by default so the live demo works immediately after account creation.

You can turn off Didit Network trust when you want explicit issuer approval. For example, a verifier can start in the demo-friendly default, then disable the framework and trust only the government, university, employer, or partner issuers it accepts.

<Info>
  Trusting Didit Network does not skip cryptography. During verification, Didit ID still checks the credential signature against issuer keys, holder key binding, audience, nonce, expiry, and revocation status.
</Info>

## Framework trust

A trust framework is a policy context for a credential ecosystem. It tells your verifier which governance applies before it accepts a credential.

Use framework-level trust when the governance is the trust decision. For example, a verifier may trust every issuer in a national identity framework, every member of a company group, or every issuer in the Didit Network sandbox.

Didit ID exposes framework entries through [`GET /trust-frameworks`](/api-reference/trust/trust-frameworks-get). You can inspect one framework with [`GET /trust-frameworks/{slug}`](/api-reference/trust/trust-frameworks-slug-get) and update account trust with [`PUT /trust-frameworks/{slug}/trust`](/api-reference/trust/trust-frameworks-slug-trust-put).

## Per-issuer overrides

Framework trust can still have exceptions. If you trust a framework but need to reject one issuer inside it, add an issuer override.

Use overrides for risk, compliance, business, or rollout reasons. The verifier still accepts the rest of the framework, but credentials from the blocked issuer fail trust policy.

Create overrides with [`POST /trust-frameworks/{slug}/issuer-overrides`](/api-reference/trust/trust-frameworks-slug-issuer-overrides-post).

## Individual trusted issuers

A trusted issuer entry says that your account accepts credentials from one issuer. Use it when you do not want to trust the full framework, or when the issuer is not covered by a framework you accept.

<ParamField path="name" type="string">
  Human-readable issuer name, such as `State University Registrar`.
</ParamField>

<ParamField path="iss" type="string">
  The issuer identifier that appears in the SD-JWT VC. This value is immutable after the issuer is created.
</ParamField>

<ParamField path="trust_anchor" type="string">
  The trust anchor type. Use a JWKS endpoint, `did:web`, or x509 material depending on the issuer ecosystem.
</ParamField>

<ParamField path="jwks_uri" type="string">
  The JWKS URI Didit ID can use to resolve issuer signing keys when the trust anchor is JWKS-based.
</ParamField>

<ParamField path="did" type="string">
  The issuer DID when the trust anchor uses `did:web`.
</ParamField>

<ParamField path="framework" type="string">
  The framework the issuer belongs to.
</ParamField>

You can edit the issuer name, trust anchor, JWKS URI, DID, and framework with [`PATCH /trusted-issuers/{uuid}`](/api-reference/trust/trusted-issuers-uuid-patch). The issuer identifier (`iss`) is the stable trust identity and cannot be changed.

## Issuer validation

When you add or update a trusted issuer, Didit ID resolves the issuer against its published SD-JWT VC issuer metadata at `/.well-known/jwt-vc-issuer` and the issuer's keys. The console shows the validation status so operators can see whether the issuer record is resolvable.

You can trigger validation through [`POST /trusted-issuers/{uuid}/validate`](/api-reference/trust/trusted-issuers-uuid-validate-post).

Validation helps you configure the trust registry, but it does not replace verification. At verification time, Didit ID always checks the credential signature against issuer keys before applying the trust policy.

## Relying-party policies

A relying party is a verifier application, brand, product, or journey that asks wallets for presentations. Each relying party can:

- Inherit the account trust policy.
- Define its own accepted frameworks.
- Define its own accepted individual issuers.
- Block specific issuers inside frameworks it otherwise trusts.

Use per-relying-party policy when one account operates many verifiers. For example, an account can model multiple airlines, banks, or brands as separate relying parties, each with its own trust requirements.

Register relying parties with [`POST /relying-parties`](/api-reference/trust/relying-parties-post), list them with [`GET /relying-parties`](/api-reference/trust/relying-parties-get), and update policy with [`PATCH /relying-parties/{uuid}`](/api-reference/trust/relying-parties-uuid-patch).

## How verification uses trust

When you create a presentation request with [`POST /presentations/request`](/api-reference/verification/presentations-request-post), you send the credential type, requested claims, and relying-party audience. Didit ID builds the DCQL request and stores the verification context.

<Steps>
  <Step title="Create a presentation request">
    Didit ID records `requested_vct`, `requested_claims`, `aud`, the nonce, and the relying-party context.
  </Step>
  <Step title="Receive the wallet response">
    The holder submits a selective-disclosure `vp_token` to [`POST /presentations/{uuid}/response`](/api-reference/verification/presentations-uuid-response-post).
  </Step>
  <Step title="Check cryptography and lifecycle">
    Didit ID verifies the issuer signature, holder key binding, audience, nonce, algorithm allowlist, expiry, and Token Status List revocation state.
  </Step>
  <Step title="Apply trust policy">
    Didit ID evaluates the credential issuer against the relying party's policy. If the relying party inherits account trust, the account policy is used.
  </Step>
</Steps>

The verification response returns `verdict`, `disclosed_claims`, and `checks`. Issuer trust contributes to the final `verdict`.

<Warning>
  Do not rely on signature validation alone. A credential can be well-formed, correctly signed, unexpired, and unrevoked, but still rejected because the issuer is not accepted by the applicable trust policy.
</Warning>

<Accordion title="What happens if I pass trusted_iss?">
  `trusted_iss` narrows the request to a specific issuer. The submitted credential must still pass the relying party's trust policy during verification.
</Accordion>

<Accordion title="Can I accept every issuer in a framework?">
  Yes. Trust the framework to accept its member issuers. Add issuer overrides when you need exceptions.
</Accordion>

<Accordion title="Can one relying party trust a different issuer set than another?">
  Yes. Relying parties can inherit account trust or define their own framework and issuer policy.
</Accordion>
