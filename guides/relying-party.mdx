A relying party is a verifier application. It asks a holder to prove something, then acts on Didit ID's `verdict`.

This guide builds an age gate for an `AgeOver18` credential. The verifier asks for `over_18`; the wallet presents only that claim; Didit ID checks cryptography, lifecycle state, and the relying party's trust policy before returning the result.

</Warning>

## Relying-party trust policy

Each relying party can inherit the account trust policy or define its own accepted frameworks and issuers. Didit ID applies that policy automatically when the wallet submits the `vp_token`.

Use per-relying-party policy when the same account operates multiple verifier experiences. For example, one account can model several brands, airlines, campuses, or banking journeys as separate relying parties, each with its own trust policy.

<Steps>
  <Step title="Create or select the relying party">
    Register the verifier with [`POST /relying-parties`](/api-reference/trust/relying-parties-post), or select an existing relying party in the console.
  </Step>
  <Step title="Choose the policy mode">
    Let the relying party inherit account trust, or define the frameworks and issuers it accepts.
  </Step>
  <Step title="Add exceptions">
    Block specific issuers inside trusted frameworks when a verifier needs a narrower policy.
  </Step>
  <Step title="Verify normally">
    Create presentation requests as usual. Didit ID enforces the relying-party policy during verification.
  </Step>
</Steps>

<Info>
  New accounts trust the Didit Network framework by default so the sandbox demo works immediately. Turn it off when you want explicit issuer approval.
</Info>

## The verification flow

<Steps>
  <Step title="Create a presentation request">
    Your backend calls `POST /v1/presentations/request` with the credential type, requested claims, and relying-party audience. The audience identifies the verifier context for request binding and policy.
  </Step>
  <Step title="Hand off to the wallet">
    Render a QR code and a same-device link to the wallet at `https://wallet-idv0.staging.didit.me/present?request=<uuid>`. The holder scans on mobile or opens the link on the same device.
  </Step>
  <Step title="Holder approves disclosure">
    The wallet shows the relying party, credential type, issuer, and requested claims. For the age gate, the holder approves `over_18` without revealing a birth date.
  </Step>
  <Step title="Poll for the verdict">
    Poll the public `GET /v1/presentations/{uuid}` until the request reaches a terminal status. The response includes `verdict` and `checks`, but not claim values.
  </Step>
  <Step title="Read the disclosed claims">
    Once verified, your backend calls `GET /v1/verifications/{uuid}` with the tenant API key to read `disclosed_claims`.
  </Step>
</Steps>

## Step 1: create the request

Call `POST /v1/presentations/request` from your backend. Didit ID creates the presentation record, generates a nonce, builds the [DCQL](/concepts/openid4vp) query, and records the relying-party context.

<ParamField body="requested_vct" type="string" required>
  The credential type. The age gate uses `AgeOver18`.
</ParamField>

<ParamField body="requested_claims" type="string[]" required>
  The claim names the wallet may disclose, such as `over_18`.
</ParamField>

<ParamField body="aud" type="string" required>
  The relying-party audience. The wallet binds it into the presentation so Didit ID can check `aud`.
</ParamField>

<ParamField body="trusted_iss" type="string">
  Optional issuer filter. When set, the submitted credential must match that issuer and still pass the relying party's trust policy.
</ParamField>

<CodeGroup>
```bash cURL
PRESENTATION="$(
  curl -sS -X POST "https://idv0.staging.didit.me/v1/presentations/request" \
    -H "Authorization: Bearer $DIDIT_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{
      "requested_vct": "AgeOver18",
      "requested_claims": ["over_18"],
      "aud": "age-gate-rp",
      "trusted_iss": ""
    }'
)"

PRESENTATION_ID="$(echo "$PRESENTATION" | jq -r '.uuid')"
echo "$PRESENTATION" | jq '{uuid, nonce, status}'
```

```js JavaScript
const response = await fetch("https://idv0.staging.didit.me/v1/presentations/request", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.DIDIT_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    requested_vct: "AgeOver18",
    requested_claims: ["over_18"],
    aud: "age-gate-rp",
    trusted_iss: "",
  }),
});

const presentation = await response.json();
const presentationId = presentation.uuid;
```

```python Python
import os
import requests

response = requests.post(
    "https://idv0.staging.didit.me/v1/presentations/request",
    headers={"Authorization": f"Bearer {os.environ['DIDIT_API_KEY']}"},
    json={
        "requested_vct": "AgeOver18",
        "requested_claims": ["over_18"],
        "aud": "age-gate-rp",
        "trusted_iss": "",
    },
)

presentation = response.json()
presentation_id = presentation["uuid"]
```

## Step 2: hand off to the wallet

Give the browser two ways to reach the wallet: a QR code for a mobile handoff and a same-device link. Both point at the wallet's present route with the presentation `uuid`. The wallet never redirects on its own; your page learns the outcome by polling (step 3). An optional `return_to` parameter only renders an explicit "return" button, and the hosted wallet honors it for `localhost` origins in development builds only, so do not rely on it in the sandbox.

```js
const WALLET = "https://wallet-idv0.staging.didit.me";

function walletPresentUrl({ presentationId }) {
  const url = new URL(`${WALLET}/present`);
  url.searchParams.set("request", presentationId);
  return url.toString();
}

const handoff = walletPresentUrl({ presentationId });
```

<Note>
  On browsers that support the W3C Digital Credentials API, you can invoke a compatible wallet inline with `navigator.credentials.get({ digital })`. The QR and same-device link pattern is the universal fallback and matches the live VeriBank demo.
</Note>

## Step 3: poll for the verdict

Poll the public `GET /v1/presentations/{uuid}` until the presentation reaches a terminal status. This endpoint is safe to call from the browser because it returns `status`, `verdict`, and `checks`, but not disclosed claim values.

<CodeGroup>
```bash cURL
curl -sS "https://idv0.staging.didit.me/v1/presentations/$PRESENTATION_ID" | jq '{status, verdict, checks}'
```

```js JavaScript
async function pollVerdict(presentationId, { intervalMs = 1500, timeoutMs = 120000 } = {}) {
  const deadline = Date.now() + timeoutMs;
  while (Date.now() < deadline) {
    const response = await fetch(
      `https://idv0.staging.didit.me/v1/presentations/${presentationId}`
    );
    const state = await response.json();
    if (state.status && state.status !== "pending") {
      return state;
    }
    await new Promise((resolve) => setTimeout(resolve, intervalMs));
  }
  throw new Error("Presentation timed out");
}

const state = await pollVerdict(presentationId);
```

```python Python
import time

def poll_verdict(presentation_id, interval=1.5, timeout=120):
    deadline = time.time() + timeout
    while time.time() < deadline:
        response = requests.get(
            f"https://idv0.staging.didit.me/v1/presentations/{presentation_id}"
        )
        state = response.json()
        if state.get("status") and state["status"] != "pending":
            return state
        time.sleep(interval)
    raise TimeoutError("Presentation timed out")

state = poll_verdict(presentation_id)
```
</CodeGroup>

Treat `verdict` as the decision. Use the `checks` map to explain a failure: `signature`, `key_binding`, `aud`, `nonce`, `alg_allowlist`, `not_expired`, and `not_revoked`. Issuer trust also contributes to the final verdict.

## Step 4: read the disclosed claims

The public poll endpoint never returns claim values. Once the verdict is `verified`, read the disclosed claims from the tenant-authenticated verification log with `GET /v1/verifications/{uuid}`. Use the same `uuid`.

<CodeGroup>
```bash cURL
curl -sS "https://idv0.staging.didit.me/v1/verifications/$PRESENTATION_ID" \
  -H "Authorization: Bearer $DIDIT_API_KEY" | jq '{verdict, disclosed_claims, checks}'
```

```js JavaScript
async function readDisclosedClaims(presentationId) {
  const response = await fetch(
    `https://idv0.staging.didit.me/v1/verifications/${presentationId}`,
    {
      headers: {
        Authorization: `Bearer ${process.env.DIDIT_API_KEY}`,
      },
    }
  );
  return response.json();
}

const verification = await readDisclosedClaims(presentationId);
if (verification.verdict === "verified" && verification.disclosed_claims.over_18) {
  // grant access
}
```

```python Python
def read_disclosed_claims(presentation_id):
    response = requests.get(
        f"https://idv0.staging.didit.me/v1/verifications/{presentation_id}",
        headers={"Authorization": f"Bearer {os.environ['DIDIT_API_KEY']}"},
    )
    return response.json()

verification = read_disclosed_claims(presentation_id)
if verification["verdict"] == "verified" and verification["disclosed_claims"].get("over_18"):
    ...  # grant access
```
